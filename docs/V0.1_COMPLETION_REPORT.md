# Local Agent Scheduler V0.1.2 Correctness Closure Report

Status: provider-free correctness closure complete; earlier V0.1.2 worker,
RootBridge, Result consumption, and full live smoke passed; post-closure worker
rerun passed while surrogate RootBridge delivery timed out

Package: `local-agent-scheduler 0.1.2`

V0.1.2 closes the V0.1 correctness audit without adding features. `Incarnation`
is one physical embodiment rather than an Execution wrapper: READY agents may
have no physical presence, and a genuinely resident Incarnation may host
sequential Executions with at most one active Execution. The current Codex
adapter still creates and closes one physical session per Execution.

## Implemented scope

V0.1 implements a single-process, local-first Scheduler backed by SQLite WAL.
It owns durable Batch, Task, Attempt, Lease, Execution, Result, Failure,
Escalation, LogicalAgent, Incarnation, PoolPartition, Workstream, Checkpoint,
topology revision, and notification outbox state.

Execution is explicitly at-least-once. Authoritative mutations require a
current Attempt, ACTIVE unexpired Lease, matching fencing epoch, and matching
`task.current_attempt_id`. No exactly-once claim is made.

The process contains a pool reconciler, dispatcher, startup recovery path,
Result Queue, notification outbox, Codex app-server ExecutionAdapter, Codex
app-server RootBridge, provider-free filesystem RootBridge, strict TOML config,
and diagnostic/control CLI.

## State machines and transaction boundaries

The frozen transition matrices are in [V0.1_SPEC.md](V0.1_SPEC.md). The critical
single-transaction boundaries are:

1. Batch, Task graph, dependencies, and initial eligibility.
2. Claim, fencing increment, Attempt, Lease, and LogicalAgent assignment.
3. Success ACK, Attempt/Lease close, Task completion, Result AVAILABLE,
   dependency release, and Batch recomputation. Only a resulting Batch/control
   transition inserts a Root wakeup event.
4. Failure recording plus deterministic retry, or suspension plus Escalation
   and decision-required notification.
5. Fenced checkpoint promotion and bounded continuity replacement.
6. Topology revisions with partition upsert/resize/capacity movement, MERGE,
   guarded retirement, drain, and future Task-classification migration.

`Task COMPLETED + Result AVAILABLE` is atomic. Root notification and Result ACK
are later independent operations and cannot roll back Task or Batch state.

## Schema summary

Schema version 4 is recorded in `schema_migrations`. SQLite runs with foreign
keys, WAL, `synchronous=FULL`, and `BEGIN IMMEDIATE` writes. Partial unique
indexes prevent multiple ACTIVE Attempts/Leases for one Task, multiple ACTIVE
Attempts for one LogicalAgent, and multiple open Escalations. Each Attempt has
at most one Execution history row and every V0.1 Task is mandatory at its Batch
barrier; ambiguous legacy authority fails migration instead of being silently
normalized. Results are unique per Task. V0.1.2 additionally enforces one
STARTING/WARM/COLD Incarnation per LogicalAgent and one active Execution per
Incarnation. Attempt-to-Incarnation binding is nullable until physical dispatch.
The transactional v1→v2 migration splits legacy reused
Incarnations into monotonically increasing generations; v2→v3 then relaxes the
Codex-specific total-Execution constraint while preserving history; v3→v4
closes Agent/Attempt/Execution uniqueness and removes optional Task state.

Runtime state exists only in SQLite. TOML bootstraps topology once; thereafter
the SQLite topology revision is authoritative across restart. TOML also contains
human-authored policy and
external integration references. No scheduler state database, registry, or
provider routing layer exists outside SQLite.

## Recovery and writer safety

Daemon startup moves through `RECOVERY` before `READY`. Overdue Leases are
fenced before execution observation, so a late heartbeat cannot revive expired
authority. Still-authoritative Codex executions are reconciled by persisted
thread and exact turn identity. Stale terminal outcomes update only their exact
Execution/Incarnation physical history; they cannot mutate Task, Result,
checkpoint, continuity, or replacement authority. Late confirmed quiescence
may refine an old LOST Incarnation to TERMINATED.

Read-only work follows its declared retry policy. A shared-workspace writer is
not replaced merely because its Lease expired. Replacement requires confirmed
quiescence or an ExecutionTarget that declares attempt isolation; otherwise the
Task and Batch suspend and a `WRITER_QUIESCENCE_UNKNOWN` Escalation is created.
The LogicalAgent also remains unavailable for unrelated work. Cancellation
revokes authority but applies the same physical-quiescence guard; the explicit
`release_cancelled_writer` recovery operation is required before revival.
Current workspace state is authoritative for a subsequently approved retry.

Each fresh Codex physical session/thread Execution receives a fresh Incarnation
generation. Confirmed terminal/quiescent completion closes that exact
Incarnation as TERMINATED; lost or unconfirmed presence becomes LOST. COLD is
reserved for future detachable presence and is treated as active even though
V0.1.2 creates none. Physical Incarnation loss does not retire LogicalAgent
identity. Logical revival restores availability; physical birth happens only at
dispatch. RETIRED is semantic death and cannot revive. Required affinity with
no compatible live identity causes a newborn LogicalAgent synchronized from
Workstream project state.

MERGE is one topology transaction: all nonterminal source Tasks receive the
target as their future scheduling classification, source and target declared
capacities are added, LogicalAgent membership/pending transitions are updated,
and the source becomes inactive. Existing Attempts and Executions retain their
frozen authority and target/profile. RETIRE refuses to commit while any
nonterminal Task remains. Pool excess closes unassigned
INITIALIZING/READY/REVIVING identities directly; only ASSIGNED identities drain.
For an idle READY identity crossing ExecutionTarget, the transaction fences an
inactive reusable Incarnation as LOST and moves the same identity immediately;
there is no unassigned DRAINING state that requires manual physical-loss input.

Partition upsert is create-or-idempotent only. Existing structural fields are
immutable in V0.1, capacity changes use resize, inactive partitions cannot be
reactivated, and unavailable configured target/profile references are rejected
or normalized as `RESOURCE_UNAVAILABLE` before they can escape a dispatcher
tick.

## Execution and Root boundaries

Scheduler Core imports no Codex, DeepSeek, CCR, TokenRhythm, provider, or model
mechanics. `ExecutionAdapter` exposes start, observe, interrupt, terminate,
outcome collection, and start reconciliation. `RootBridge` is separately
injected and cannot mutate scheduling state.

The daemon runs a narrow notifier thread that owns only
`notification_outbox → RootBridge.deliver → delivery/backoff`. Dispatcher
execution observation and Lease heartbeat supervision remain independent, so a
slow bounded RootBridge turn cannot pause Scheduler control. Root remains
notification-driven and does not poll Scheduler state. Retry backoff and
delivery timestamps are anchored to bridge-call completion rather than start.

The Codex adapter uses official app-server JSONL methods: `thread/start`,
`turn/start`, `thread/read`, and `turn/interrupt`. The Codex RootBridge uses
`thread/resume` and a notification `turn/start`, waiting for the matching
`turn/completed`. If the live terminal notification is missed, RootBridge reads
the persisted thread and reconciles only the exact turn ID returned by its own
`turn/start`. This bounded transport reconciliation does not make Root poll
Scheduler state; Root remains dormant until notified. Notification text contains
event identity and entity indexes, not Result payload.

Adding an OpenCode adapter requires a new adapter implementation and
configuration/CLI selection; it does not require changing Core state machines.

## Live acceptance evidence

The bounded sandbox-external smoke used the installed Codex CLI 0.147.0 and
existing authenticated deployment without reading or changing credentials,
provider routes, CCR, or global Codex configuration. It proved:

1. Task QUEUED → LEASED/RUNNING through real `thread/start` + `turn/start`.
2. The read-only worker returned
   `{"status":"ok","evidence":"v0.1.1-live-smoke"}`.
3. Execution SUCCEEDED with terminal/quiescent confirmation; its generation-1
   Incarnation became TERMINATED.
4. Task and Batch became COMPLETED atomically with Result AVAILABLE.
5. The then-current V0.1.1 implementation delivered both RESULT_AVAILABLE and
   BATCH_RESULTS_READY. V0.1.2 deliberately removes the per-Result wakeup; this
   historical smoke remains evidence for transport, not the new wakeup count.
6. Codex RootBridge resumed an idle persisted thread and completed one matching
   notification turn with `delivery=true`.
7. Root consumption changed the actual worker Result from AVAILABLE to ACKED.
8. Final database integrity was `ok`, with no active Lease or Escalation.

Live hardening also found two pre-request deployment mismatches and one
execution-lifetime mismatch: the Windows script launcher could not be passed
directly to `Popen`, current Codex requires `workspace-write` rather than the
old `workspaceWrite`, and the old `daemon --once` exited immediately after
dispatch and interrupted its child turn. The repository now uses the current
sandbox spelling, rejects unknown sandbox values, preserves one-shot live
sessions until idle, and classifies a persisted interruption as
`EXECUTION_LOST`. The Windows deployment profile used the concrete Node + Codex
JavaScript entrypoint; Core semantics remain unchanged.

The RootBridge smoke target was the completed worker thread because a newly
created zero-turn thread has no rollout and cannot be resumed. Production still
requires a configured existing Root thread ID; RootBridge does not create or
own that thread.

The sanitized acceptance record is
[V0.1.1_LIVE_ACCEPTANCE.md](V0.1.1_LIVE_ACCEPTANCE.md). It intentionally omits
thread/event identifiers, prompts, credentials, and request bodies.

A new V0.1.2 live smoke is recorded in
[V0.1.2_LIVE_ACCEPTANCE.md](V0.1.2_LIVE_ACCEPTANCE.md). Its real read-only worker,
Task/Result/Batch flow, Batch-level-only outbox, Codex RootBridge delivery, and
Root Result consumption all passed. After the restarted Codex process loaded an
explicit local HTTP/HTTPS proxy, the final worker completed in 6.835 seconds and
the notification turn reached confirmed delivery in 155.458 seconds. The Result
became ACKED, database integrity was `ok`, and no active Lease or open Escalation
remained. An earlier 600.534-second timeout exposed the lost-live-terminal gap;
exact-turn persisted reconciliation and provider-free completed/interrupted
regressions now close it without making Root poll Scheduler state.

## How to diagnose

Use `status`, then inspect the authoritative entities:

```powershell
local-agent-scheduler --config config/scheduler.example.toml status
local-agent-scheduler --config config/scheduler.example.toml task list
local-agent-scheduler --config config/scheduler.example.toml execution list
local-agent-scheduler --config config/scheduler.example.toml result list
local-agent-scheduler --config config/scheduler.example.toml escalation list
local-agent-scheduler --config config/scheduler.example.toml outbox list
local-agent-scheduler --config config/scheduler.example.toml pool show
local-agent-scheduler --config config/scheduler.example.toml pool resize general 4
local-agent-scheduler --config config/scheduler.example.toml pool move-capacity source target 2
```

Use `recover` after an unclean stop. Resolve an Escalation only after inspecting
its snapshot. A writer retry requires `--confirm-quiescent`; otherwise it remains
suspended. Use execution interrupt/terminate when a runtime still has an
attachable physical handle. Never repair authority by editing SQLite manually.

## Known limitations and deferred features

* V0.1 is single-machine and single-daemon; there is no HA or leader election.
* Codex creates a dedicated physical thread per Execution and therefore a fresh
  Incarnation. Warm thread reuse is not implemented; Core now permits a future
  adapter to reuse only the same still-live physical embodiment for sequential
  Executions.
* Shared-workspace writer isolation is not implemented. Unknown quiescence
  therefore suspends instead of launching a replacement.
* Continuity is a bounded structured capsule, not a transcript or vector-memory
  service.
* Pool SPLIT, workflow DSL, automatic decomposition, semantic recovery planning,
  dashboards, provider routing, and credential pools are deferred.
* The current configuration loader wires the first adapter type, Codex
  app-server. Adding another target type changes adapter/configuration wiring,
  not Core.
* Each PoolPartition still selects exactly one execution target/profile. A
  mixed-terminal eligible-target policy is deliberately deferred until a
  second terminal exists; Task/Attempt/Lease/Result/Batch/LogicalAgent state
  machines do not need to change for that later adapter work.
* The example command remains the portable `codex app-server` form. On this
  Windows deployment, a concrete Node + Codex JavaScript entrypoint was needed
  when launching through Python `subprocess`; deployment packaging may choose
  an equivalent executable wrapper outside Core.
* `daemon --once` is bounded by `lease_seconds` and terminates/cancels remaining
  active Executions at that boundary. Use the resident daemon for legitimately
  longer work.

## Architecture deviations

No Core Invariant was intentionally changed. The implementation does not copy
the architecture overview into a generic framework: it uses one SQLite process,
one narrow adapter protocol, one narrow RootBridge protocol, and no scheduler
LLM, RPC framework, external queue, or second runtime.

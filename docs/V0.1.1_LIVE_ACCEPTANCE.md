# V0.1.1 Live Acceptance Record

Date: 2026-08-12

Environment: Windows, installed Codex CLI 0.147.0, existing authenticated user
deployment. The smoke did not read, copy, modify, or persist credentials,
provider routes, CCR configuration, global Codex configuration, full prompts,
request bodies, thread IDs, or event IDs.

## Worker flow

One read-only Task was submitted with retry disabled. The real Codex app-server
path completed with this sanitized authoritative Result payload:

```json
{"evidence":"v0.1.1-live-smoke","status":"ok"}
```

Observed final state:

* Task: COMPLETED
* Execution: SUCCEEDED
* Attempt: SUCCEEDED
* Lease: RELEASED; no active Lease
* Incarnation generation 1: TERMINATED
* Result: AVAILABLE, then ACKED by the Root consumer
* Batch: COMPLETED
* Escalations: none
* SQLite integrity: ok

Task completion and Result availability occurred before Root consumption. The
durable RESULT_AVAILABLE and BATCH_RESULTS_READY outbox events each reached
DELIVERED with one delivery attempt.

## RootBridge flow

The Codex RootBridge resumed an idle persisted thread, started one notification
turn carrying only event identity/entity indexes, observed the matching
`turn/completed`, and returned `delivery=true`. The actual worker Result was
then consumed through the Result Queue and changed to ACKED.

A zero-turn thread was not used because current Codex reports that it has no
rollout and cannot be resumed. Production therefore still supplies an existing
Root thread ID; RootBridge neither creates nor owns Root identity.

## Hardening discoveries

The acceptance exercise found and fixed:

* that Codex build required kebab-case `workspace-write` rather than the
  `SandboxPolicy.type` discriminator `workspaceWrite`. V0.1.2 freezes
  `thread/start.params.sandbox` as Codex `SandboxMode` (`read-only` /
  `workspace-write` / `danger-full-access`) via an explicit Adapter map;
* Windows Python subprocess deployment required a concrete executable entrypoint
  rather than the shell script shim used interactively;
* the previous `daemon --once` exited immediately after dispatch and interrupted
  the live turn;
* persisted `interrupted` turns must classify as EXECUTION_LOST;
* run-to-idle needs a deterministic ceiling.

The final `daemon --once` path keeps the adapter session alive until idle and is
bounded by configured `lease_seconds`; on timeout it uses the existing
terminate/cancel safety path. The resident daemon remains the correct mode for
long-running Tasks.
